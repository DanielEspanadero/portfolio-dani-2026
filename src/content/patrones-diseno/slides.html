Fundamentos / 02

Un nombre para una solución que se repite

Un patrón describe una solución habitual a un problema que aparece una y otra vez en un contexto concreto. No es una biblioteca ni una receta obligatoria: le pone nombre a una decisión que ya sabes tomar.

El libro habla de C++ y Smalltalk de 1994 y sigue sirviendo en Java de hoy. No describe un lenguaje: describe cómo colaboran los objetos.

El catálogo original · 1994

Fundamentos / 03

Cuando todos resolvían lo mismo con nombres distintos

El problema

A principios de los noventa la orientación a objetos se volvió el paradigma dominante. Cada equipo resolvía la misma familia de problemas con nombres propios, y no había forma de comparar una solución con otra.

La idea

Buscar en proyectos reales las soluciones que se repetían y catalogarlas por el problema que resuelven, no por la técnica que usan.

El resultado

Un vocabulario común. Decir «Adapter» u «Observer» deja de ser jerga y pasa a ser un contrato de conversación entre dos personas que nunca trabajaron juntas.

Lo que no hicieron

No inventaron las soluciones: las encontraron. El catálogo no patenta patrones, los ordena para que se puedan enseñar y discutir.

Fundamentos / 04

Lo que compra un patrón, y lo que no

Lo que compra

Vocabulario compartido: una conversación sobre diseño avanza sin explicar la solución entera.

Experiencia que no tienes que repetir: el patrón ya acumula los errores de quienes lo aplicaron antes.

Decisiones documentadas: el nombre en el código explica por qué esa clase existe.

Lo que no compra

No es una bala de plata: un patrón mal aplicado añade clases, indirección y ceremonia sin resolver nada.

No justifica sobrediseño: si una función resuelve el problema, el patrón sobra.

No es obligatorio: la mayoría del código de producción no necesita ninguno de los 23.

El criterio va primero y el patrón después. Todo el resto de esta presentación es ese criterio.

GoF / Creacionales / 06

Singleton

AnalogíaUn edificio tiene una única dirección oficial, aunque muchas personas la consulten.

Problema

Varias partes necesitan la misma tabla de configuración y no deben crear copias divergentes.

class Settings { String language = "es"; }
class App {
  Settings menu = new Settings();
  Settings checkout = new Settings();
  void switchLanguage() { menu.language = "en"; }
  // El pago sigue en español.
}

Intención y roles

La propia clase controla su instancia única; los clientes acceden a ella por un punto común.

Cuándo usarlo

Cuando la identidad única es una restricción real y el ciclo de vida está bien definido.

Cómo reconocerloCambias el idioma en una copia de la configuración y descubres que otra pantalla conserva el anterior.

Coste y cuándo no

Introduce acceso global y dificulta aislar pruebas. Un enum se inicializa de forma segura entre hilos, pero eso no vuelve seguro un estado mutable que añadas. El scope singleton de Spring es por bean y contenedor, no una instancia GoF universal.

GoF / Creacionales / 07

Singleton en Java 

enum Settings {
  INSTANCE;
  String language() { return "es"; }
}
public static void main(String[] args) {
  Settings first = Settings.INSTANCE;
  Settings second = Settings.INSTANCE;
  System.out.println(first == second);
  System.out.println(first.language());
}

Recorrido

El enum crea INSTANCE una sola vez. Ambas referencias apuntan a esa instancia y devuelven el idioma. Aquí no hay estado mutable compartido.

Resultado

true
es

GoF / Creacionales / 08

Factory Method

AnalogíaCada sucursal decide qué vehículo ofrece, pero el procedimiento de envío es común.

Problema

Un proceso de envío necesita crear un transporte sin fijar su clase concreta.

class Truck { void deliver() {} }
class Logistics {
  void send() {
    Truck transport = new Truck();
    transport.deliver();
  }
}

Intención y roles

El creador define el proceso y un método de creación; una subclase redefine ese método y devuelve el producto concreto.

Cuándo usarlo

Cuando un proceso extensible debe dejar la creación de un colaborador a las subclases.

Cómo reconocerloQuieres reutilizar el envío por barco, pero el proceso lleva un new Truck incrustado.

Coste y cuándo no

Exige herencia y más clases. Un método con switch que elige productos es una fábrica simple; no es este mecanismo por redefinición. No lo introduzcas si no hay variantes del proceso.

GoF / Creacionales / 09

Factory Method en Java 

interface Transport { String deliver(); }
static class Truck implements Transport {
  public String deliver() { return "carretera"; }
}
static abstract class Logistics {
  abstract Transport createTransport();
  String send() { return createTransport().deliver(); }
}
static class RoadLogistics extends Logistics {
  @Override Transport createTransport() {
    return new Truck();
  }
}
public static void main(String[] args) {
  Logistics logistics = new RoadLogistics();
  System.out.println(logistics.send());
}

Recorrido

send pertenece al creador base. Invoca createTransport y Java despacha a la redefinición de RoadLogistics. El camión creado realiza la entrega.

Resultado

carretera

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Creacionales / 10

Abstract Factory

AnalogíaUna tienda vende conjuntos de muebles que combinan, no piezas elegidas al azar.

Problema

La interfaz visual mezcla botones claros con menús oscuros porque cada elemento se crea por separado.

record Button(String theme) {}
record Menu(String theme) {}
class Screen {
  Button button = new Button("claro");
  Menu menu = new Menu("oscuro");
}

Intención y roles

Una fábrica abstracta ofrece varios productos relacionados; cada fábrica concreta produce una familia compatible.

Cuándo usarlo

Cuando necesitas cambiar una familia completa manteniendo la coherencia entre sus productos.

Cómo reconocerloCambias el tema del botón y olvidas cambiar el menú que debe combinar con él.

Coste y cuándo no

Añadir un nuevo tipo de producto obliga a cambiar todas las fábricas. Factory Method delega una creación mediante herencia; Abstract Factory entrega una familia mediante un objeto colaborador.

GoF / Creacionales / 11

Abstract Factory en Java 

interface Button { String paint(); }
interface Menu { String paint(); }
interface ThemeFactory {
  Button button();
  Menu menu();
}
static class DarkTheme implements ThemeFactory {
  public Button button() { return () -> "botón oscuro"; }
  public Menu menu() { return () -> "menú oscuro"; }
}
public static void main(String[] args) {
  ThemeFactory theme = new DarkTheme();
  System.out.println(theme.button().paint());
  System.out.println(theme.menu().paint());
}

Recorrido

El cliente recibe una sola fábrica. Pide dos tipos de producto sin conocer sus clases y ambos pertenecen a la familia oscura. Las lambdas implementan las interfaces de un método.

Resultado

botón oscuro
menú oscuro

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Creacionales / 12

Builder

AnalogíaPreparar un bocadillo por pasos: elegir pan y después añadir ingredientes.

Problema

Un constructor con muchos parámetros opcionales resulta difícil de leer y fácil de usar mal.

record Sandwich(String bread, boolean cheese,
    boolean tomato, boolean onion, boolean sauce) {}
class Order {
  Sandwich lunch = new Sandwich(
      "integral", true, false, false, true);
}

Intención y roles

Un constructor por pasos acumula opciones y produce el objeto final. Un director de pasos es opcional.

Cuándo usarlo

Para objetos con muchas opciones o reglas de construcción, preferiblemente inmutables al terminar.

Cómo reconocerloNecesitas consultar la firma para saber qué ingrediente activa cada true del constructor.

Coste y cuándo no

Añade una clase y puede permitir combinaciones inválidas si no valida. Con dos datos obligatorios, un constructor o record suele bastar.

GoF / Creacionales / 13

Builder en Java 

record Sandwich(String bread, boolean cheese) {}
static class SandwichBuilder {
  private String bread = "integral";
  private boolean cheese;
  SandwichBuilder bread(String value) {
    bread = Objects.requireNonNull(value); return this;
  }
  SandwichBuilder cheese() { cheese = true; return this; }
  Sandwich build() { return new Sandwich(bread, cheese); }
}
public static void main(String[] args) {
  Sandwich lunch = new SandwichBuilder().cheese().build();
  System.out.println(lunch.bread() + ": " + lunch.cheese());
}

Recorrido

Cada paso devuelve el builder para encadenar llamadas. build crea un valor final independiente; modificar otro builder no altera ese bocadillo.

Resultado

integral: true

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Creacionales / 14

Prototype

AnalogíaFotocopiar una ficha y modificar el nombre en la copia.

Problema

Crear configuraciones parecidas desde cero repite valores y hace perder ajustes ya elegidos.

class Badge {
  String name, color; int fontSize = 12;
  Badge forLuis() {
    Badge next = new Badge();
    next.name = "Luis"; next.color = color;
    return next; // Olvida el tamaño elegido.
  }
}

Intención y roles

Un prototipo ofrece una operación de copia; el cliente parte de un objeto existente sin reconstruirlo campo por campo.

Cuándo usarlo

Cuando la configuración inicial es costosa o solo se conoce el objeto que debe copiarse.

Cómo reconocerloReconstruyes una ficha campo por campo y pierdes un ajuste que ya tenía la original.

Coste y cuándo no

Hay que decidir copia superficial o profunda: compartir listas mutables puede causar sorpresas. Evita clonar recursos externos; para valores pequeños, un record y un constructor pueden ser más claros.

GoF / Creacionales / 15

Prototype en Java 

record Badge(String name, List<String> colors) {
  Badge { colors = List.copyOf(colors); }
  Badge copyFor(String newName) {
    return new Badge(newName, colors);
  }
}
public static void main(String[] args) {
  Badge original = new Badge("Ana", List.of("azul"));
  Badge copy = original.copyFor("Luis");
  System.out.println(original.name() + "/" + copy.name());
}

Recorrido

copyFor crea otra ficha conservando los colores. List.copyOf impide modificar la lista compartida y los String son inmutables: aquí compartirlos es seguro.

Resultado

Ana/Luis

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Estructurales / 16

Adapter

AnalogíaUn adaptador de enchufe conecta dos formatos incompatibles sin rehacer el aparato.

Problema

Nuestro cliente espera una temperatura en Celsius, pero el sensor existente entrega Fahrenheit.

class OldSensor { int fahrenheit() { return 68; } }
class Dashboard {
  OldSensor sensor = new OldSensor();
  int room() { return (sensor.fahrenheit() - 32) * 5 / 9; }
  int chart() { return (sensor.fahrenheit() - 32) * 5 / 9; }
}

Intención y roles

El adaptador cumple el contrato esperado y traduce las llamadas al objeto adaptado.

Cuándo usarlo

Al integrar una biblioteca o sistema existente cuyo contrato no puedes cambiar.

Cómo reconocerloRepites la conversión de Fahrenheit a Celsius en cada pantalla que consulta el sensor.

Coste y cuándo no

Oculta diferencias de formato, no incompatibilidades de significado. Si controlas ambos contratos y pueden unificarse, quizá no necesitas esta capa.

GoF / Estructurales / 17

Adapter en Java 

interface Thermometer { int celsius(); }
static class OldSensor {
  int fahrenheit() { return 68; }
}
record SensorAdapter(OldSensor sensor) implements Thermometer {
  public int celsius() {
    return (sensor.fahrenheit() - 32) * 5 / 9;
  }
}
public static void main(String[] args) {
  Thermometer thermometer = new SensorAdapter(new OldSensor());
  System.out.println(thermometer.celsius());
}

Recorrido

El cliente solo conoce celsius. SensorAdapter llama al sensor viejo y convierte 68 °F en 20 °C. El redondeo entero se acepta para esta demostración.

Resultado

20

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Estructurales / 18

Bridge

AnalogíaUn mando y un televisor evolucionan por separado si comparten un protocolo de control.

Problema

Combinar tipos de aviso y canales de entrega mediante herencia crea una clase por cada combinación.

abstract class Notice { abstract String send(); }
class AlertEmail extends Notice {
  String send() { return "email: alerta"; }
}
class AlertSms extends Notice {
  String send() { return "sms: alerta"; }
}
// Un recordatorio necesita otras dos subclases.

Intención y roles

La abstracción de alto nivel mantiene una referencia a una implementación; ambas dimensiones pueden variar de forma independiente.

Cuándo usarlo

Si prevés dos ejes de variación: qué se hace y con qué mecanismo se realiza.

Cómo reconocerloAñades SMS y tienes que crear una subclase nueva por cada tipo de aviso que ya tienes.

Coste y cuándo no

Añade indirección. Adapter hace compatible algo ya existente; Bridge separa dimensiones por diseño. Con un único eje estable, una función sencilla puede bastar.

GoF / Estructurales / 19

Bridge en Java 

interface Channel { String send(String text); }
static class Email implements Channel {
  public String send(String text) { return "email: " + text; }
}
static abstract class Notice {
  final Channel channel;
  Notice(Channel channel) { this.channel = channel; }
  abstract String publish();
}
static class Alert extends Notice {
  Alert(Channel channel) { super(channel); }
  String publish() { return channel.send("alerta"); }
}
public static void main(String[] args) {
  Notice notice = new Alert(new Email());
  System.out.println(notice.publish());
}

Recorrido

Alert define el mensaje; Email define la entrega. Otra clase Notice o Channel puede añadirse sin crear una subclase para cada combinación.

Resultado

email: alerta

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Estructurales / 20

Composite

AnalogíaUna caja puede contener productos o más cajas: todo tiene un peso total.

Problema

Calcular el total de una cesta requiere tratar artículos y cajas de artículos con lógica distinta.

record Product(int price) {}
record Box(Product[] products) {}
class Checkout {
  int total(Object item) {
    if (item instanceof Product p) return p.price();
    int sum = 0; for (Product p : ((Box) item).products()) sum += p.price();
    return sum;
  } }

Intención y roles

Hoja y contenedor cumplen el mismo contrato. El contenedor delega recursivamente en sus hijos.

Cuándo usarlo

Para árboles donde una operación tiene sentido tanto en elementos individuales como en grupos.

Cómo reconocerloPreguntas si recibes un producto o una caja y debes reescribir el total al anidar otra caja.

Coste y cuándo no

Hay que controlar ciclos y definir qué operaciones pertenecen realmente a una hoja. Para listas planas, el árbol solo añade complejidad.

GoF / Estructurales / 21

Composite en Java 

interface Item { int price(); }
record Product(int price) implements Item {}
record Box(List<Item> children) implements Item {
  Box { children = List.copyOf(children); }
  public int price() {
    return children.stream().mapToInt(Item::price).sum();
  }
}
public static void main(String[] args) {
  Item box = new Box(List.of(new Product(3),
      new Box(List.of(new Product(4)))));
  System.out.println(box.price());
}

Recorrido

La caja exterior suma un producto de 3 y otra caja. Esa caja devuelve 4. El cliente llama price sin preguntar si recibe una hoja o un grupo.

Resultado

7

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Estructurales / 22

Decorator

AnalogíaVestirse por capas: cada capa añade algo y conserva lo anterior.

Problema

Queremos añadir extras a una bebida sin crear clases para todas las combinaciones posibles.

class CoffeeMenu {
  int coffee() { return 2; }
  int withMilk() { return 3; }
  int withSyrup() { return 4; }
  int withMilkAndSyrup() { return 5; }
  // La nata obliga a duplicar las combinaciones.
}

Intención y roles

Un decorador cumple el mismo contrato que el componente, lo envuelve y añade comportamiento antes o después de delegar.

Cuándo usarlo

Cuando necesitas combinar responsabilidades opcionales por instancia y en tiempo de ejecución.

Cómo reconocerloAñades nata al menú y debes escribir una variante por cada combinación de leche y sirope.

Coste y cuándo no

El orden importa y depurar muchas capas cuesta. Decorator añade responsabilidades; Proxy controla acceso o ciclo de vida. Para una sola opción estable, un parámetro puede ser suficiente.

GoF / Estructurales / 23

Decorator en Java 

interface Drink { int price(); }
static class Coffee implements Drink {
  public int price() { return 2; }
}
record Milk(Drink inner) implements Drink {
  public int price() { return inner.price() + 1; }
}
public static void main(String[] args) {
  Drink plain = new Coffee();
  Drink enriched = new Milk(plain);
  System.out.println(enriched.price());
}

Recorrido

Milk recibe cualquier Drink. Cuando el cliente pide el precio, delega al café y añade uno. El contrato sigue siendo Drink y podrían apilarse más extras.

Resultado

3

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Estructurales / 24

Facade

AnalogíaLa recepción de un hotel coordina varios servicios desde un único mostrador.

Problema

El cliente debe recordar muchas llamadas y su orden para iniciar una actividad.

class Screen { void on() {} }
class Speaker { void on() {} }
class Viewer {
  void play(Screen screen, Speaker speaker) {
    screen.on();
    speaker.on();
  }
}

Intención y roles

Una fachada ofrece una operación sencilla y coordina subsistemas. No obliga a ocultar todas sus APIs.

Cuándo usarlo

Para dar una entrada estable a un conjunto de componentes y reducir el conocimiento del cliente.

Cómo reconocerloRepites la secuencia de encender pantalla y audio en cada lugar desde el que inicias una película.

Coste y cuándo no

Puede convertirse en un objeto que hace demasiado. No debe absorber todas las reglas del sistema; si solo cambia nombres sin simplificar, no aporta valor.

GoF / Estructurales / 25

Facade en Java 

static class Screen {
  String on() { return "pantalla lista"; }
}
static class Speaker {
  String on() { return "audio listo"; }
}
record Cinema(Screen screen, Speaker speaker) {
  String start() {
    return screen.on() + ", " + speaker.on();
  }
}
public static void main(String[] args) {
  Cinema cinema = new Cinema(new Screen(), new Speaker());
  System.out.println(cinema.start());
}

Recorrido

El cliente llama start una vez. Cinema enciende primero la pantalla y luego el sonido. La coordinación queda en un lugar, no repetida en cada cliente.

Resultado

pantalla lista, audio listo

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Estructurales / 26

Flyweight

AnalogíaUn sello comparte su dibujo; cada estampación decide dónde colocarlo.

Problema

Miles de caracteres repiten la misma información tipográfica y consumen memoria innecesaria.

class Letter {
  char symbol = 'A'; int x;
  byte[] glyphPixels = new byte[4096];
}
class Page {
  Letter first = new Letter(), second = new Letter();
  // Dos letras A reservan dos imágenes iguales.
}

Intención y roles

La fábrica comparte estado intrínseco inmutable; el cliente aporta el estado extrínseco que varía en cada uso.

Cuándo usarlo

Cuando hay muchos objetos y una parte importante de sus datos puede compartirse de forma segura.

Cómo reconocerloGuardas miles de letras A y reservas una copia de la misma imagen tipográfica en cada una.

Coste y cuándo no

Gestionar la caché y separar estados tiene coste. No compartas coordenadas u otros datos mutables por accidente. Mide memoria antes de añadir esta optimización.

GoF / Estructurales / 27

Flyweight en Java 

record Glyph(char symbol) {
  String draw(int x) { return symbol + "@" + x; }
}
static class GlyphPool {
  private final Map<Character, Glyph> cache = new HashMap<>();
  Glyph get(char symbol) {
    return cache.computeIfAbsent(symbol, Glyph::new);
  }
}
public static void main(String[] args) {
  GlyphPool pool = new GlyphPool();
  Glyph first = pool.get('A');
  System.out.println(first == pool.get('A'));
  System.out.println(first.draw(10));
}

Recorrido

El símbolo inmutable se comparte. La posición 10 se pasa a draw y no se guarda en el Glyph. La caché es local y este ejemplo no promete seguridad concurrente.

Resultado

true
A@10

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Estructurales / 28

Proxy

AnalogíaUn portero deja pasar solo a quien tiene autorización.

Problema

Queremos controlar el acceso a un documento sin cambiar el contrato que conoce su lector.

class Report { String read() { return "informe"; } }
class Readers {
  String preview(Report doc, boolean allowed) {
    return allowed ? doc.read() : "acceso denegado";
  }
  String download(Report doc) {
    return doc.read(); // Aquí olvidaste el permiso.
  } }

Intención y roles

El sustituto implementa el contrato del objeto real y decide si, cuándo o cómo delegar.

Cuándo usarlo

Para permisos, carga diferida, acceso remoto o caché detrás de una interfaz común.

Cómo reconocerloCompruebas el permiso al previsualizar el informe, pero olvidas hacerlo al descargarlo.

Coste y cuándo no

Puede esconder latencia o errores que el cliente debe conocer. A diferencia de Decorator, su intención central es controlar acceso. Evítalo si una llamada directa resulta suficiente.

GoF / Estructurales / 29

Proxy en Java 

interface Document { String read(); }
static class Report implements Document {
  public String read() { return "informe"; }
}
record Guarded(Document target, boolean allowed)
    implements Document {
  public String read() {
    if (!allowed) return "acceso denegado";
    return target.read();
  }
}
public static void main(String[] args) {
  Document doc = new Guarded(new Report(), false);
  System.out.println(doc.read());
}

Recorrido

El lector usa Document. Guarded comprueba la autorización y no llama a Report cuando se deniega. El booleano ilustra la decisión; no es un sistema real de seguridad.

Resultado

acceso denegado

Java 25 · ejemplo mínimo pedagógico. Importaciones: java.util.* y java.util.function.*.

GoF / Comportamiento / 30

Chain of Responsibility

AnalogíaEn una oficina, cada mesa resuelve un trámite o lo pasa a la siguiente.

Problema

Una petición necesita pasar por comprobaciones configurables sin que el emisor conozca todas.

class Form {
  String submit(String text, boolean loggedIn) {
    if (!loggedIn) return "inicia sesión";
    if (text.isBlank()) return "vacío";
    if (text.length() > 10) return "demasiado largo";
    return "aceptado";
  }
}

Intención y roles

Cada manejador atiende o rechaza la petición; si corresponde, delega en el siguiente eslabón.

Cuándo usarlo

Service Layer

AnalogíaUn coordinador organiza un trámite completo sin obligarte a hablar con cada departamento.

Problema

Cada punto de entrada repite la secuencia de comprobar datos y guardar una reserva.

class BookingEntries {
  java.util.List<String> names = new java.util.ArrayList<>();
  void web(String name) {
    if (!name.isBlank()) names.add(name);
  }
  void console(String name) {
    if (!name.isBlank()) names.add(name);
  } }

Intención y roles

La capa de servicio ofrece casos de uso y coordina colaboradores; las reglas propias de los objetos pueden seguir en el dominio.

Cuándo usarlo

Cuando una operación de aplicación se usa desde varios canales o coordina varias dependencias.

Cómo reconocerloAñades una validación a la reserva web y tienes que acordarte de repetirla en la entrada por consola.

Coste y cuándo no

No es GoF ni exige un servicio por cada clase. Evita servicios gigantes o meros pasamanos. En Spring, las transacciones necesitan configuración y límites explícitos; este ejemplo en memoria no implementa transacciones ni reservas concurrentes.

Service Layer en Java 

interface Reservations { void save(String name); }
record BookingService(Reservations reservations) {
  String book(String name) {
    if (name.isBlank()) throw new IllegalArgumentException("nombre");
    reservations.save(name);
    return "reserva confirmada";
  }
}
public static void main(String[] args) {
  List<String> names = new ArrayList<>();
  BookingService service = new BookingService(names::add);
  System.out.println(service.book("Ana"));
  System.out.println(names.size());
}

Recorrido

book valida antes de delegar el guardado. El cliente recibe el resultado del caso de uso. En Spring este servicio podría ser un bean inyectado por constructor; una anotación por sí sola no define la consistencia del sistema.

Specification

AnalogíaUn filtro de búsqueda combina requisitos: barato y disponible.

Problema

Las reglas para seleccionar productos se repiten y queremos combinarlas sin copiar condiciones.

record Product(int price, boolean available) {}
class Offers {
  void homepage(Product[] items) {
    for (var p : items) if (p.price() <= 10) System.out.println(p);
  }
  void newsletter(Product[] items) {
    for (var p : items) if (p.price() <= 10 && p.available()) System.out.println(p);
  } }

Intención y roles

Una especificación encapsula una condición de negocio y puede componerse con otras mediante operadores lógicos.

Cuándo usarlo

Para criterios reutilizables con significado y combinaciones reales en el dominio.

Cómo reconocerloCambias el límite de precio y debes buscar cada condición copiada, sola o combinada con disponibilidad.

Coste y cuándo no

No pertenece a GoF. Para una condición aislada basta un if. Un Predicate en memoria no se convierte automáticamente en SQL, el lenguaje de consulta de bases de datos. La API Specification de Spring Data JPA requiere criterios traducibles a consultas.

Specification en Java 

record Product(int price, boolean available) {}
public static void main(String[] args) {
  Predicate<Product> affordable = product -> product.price() <= 10;
  Predicate<Product> available = Product::available;
  Predicate<Product> eligible = affordable.and(available);
  Product book = new Product(8, true);
  Product expensive = new Product(20, true);
  System.out.println(eligible.test(book));
  System.out.println(eligible.test(expensive));
}

Recorrido

Cada Predicate es una condición ejecutable. and crea una regla compuesta y test la evalúa. El producto de 8 cumple ambas; el de 20 no. Java ya ofrece esta composición, no hace falta inventar una jerarquía.

Circuit Breaker y Retry

AnalogíaRetry vuelve a llamar unas pocas veces. Un fusible abierto deja de llamar hasta que pueda probarse la recuperación.

Problema

Una lectura remota falla temporalmente; insistir sin límite sobre un servicio caído empeora la sobrecarga.

class StockClient {
  String read(java.util.concurrent.Callable<String> remote) {
    while (true) { try { return remote.call(); }
      catch (Exception failure) {} } // Sin pausa ni límite.
  } }

Intención y roles

Retry limita intentos ante fallos transitorios; Circuit Breaker registra fallos y corta llamadas. Un circuito real usa cerrado, abierto y semiabierto para probar recuperación.

Cuándo usarlo

En integraciones remotas con tiempos límite y operaciones idempotentes: repetirlas no debe duplicar efectos. Las lecturas suelen encajar; un cobro exige clave de idempotencia y garantías del receptor.

Cómo reconocerloEl proveedor de stock cae y sigues llamándolo sin pausa ni límite, aunque ninguna lectura responde.

Coste y cuándo no

No son GoF ni capacidades automáticas de Spring. El ejemplo abre tras una operación agotada y no se recupera: omite temporización, semiabierto, esperas crecientes con variación aleatoria, métricas y concurrencia. No es producción. No reintentes errores de validación ni operaciones no idempotentes sin garantías.

Circuit Breaker y Retry en Java 

static class Circuit {
  private boolean open;
  String read(Supplier<String> remote) {
    if (open) return "abierto";
    for (int attempt = 1; attempt <= 3; attempt++) {
      try { return remote.get(); }
      catch (IllegalStateException transientFailure) {
        if (attempt == 3) { open = true; return "agotado"; }
      }
    }
    throw new AssertionError();
  }
}
public static void main(String[] args) {
  Circuit circuit = new Circuit();
  Supplier<String> failingRead = () -> {
    System.out.println("intento");
    throw new IllegalStateException("fallo transitorio simulado");
  };
  System.out.println(circuit.read(failingRead));
  System.out.println(circuit.read(failingRead));
}

Recorrido

Tras tres fallos se abre el circuito: la siguiente lectura no llama al remoto. IllegalStateException representa aquí solo el fallo transitorio simulado. No hay recuperación automática ni seguridad concurrente.

Práctica y criterio / 64

Empieza por lo que cambia

¿Cómo nace el objeto?

Un método de subclase → Factory Method.
Una familia compatible → Abstract Factory.
Muchos pasos u opciones → Builder.
Copiar configuración → Prototype.
Identidad única imprescindible → Singleton.

¿Cómo se conecta?

Contrato incompatible → Adapter.
Dos ejes independientes → Bridge.
Árbol uniforme → Composite.
Capas opcionales → Decorator.
Entrada sencilla → Facade.
Compartir datos inmutables → Flyweight.
Controlar acceso → Proxy.

Primero escribe el problema sin nombres de patrones. Si el cambio no es real ni probable, conserva la solución más pequeña.

Práctica y criterio / 65

¿Quién decide y quién recuerda?

Variar o coordinar

Elegir algoritmo → Strategy.
Cambiar de modo → State.
Fijar pasos → Template Method.
Centralizar interacciones → Mediator.
Pasar por filtros → Chain of Responsibility.
Notificar cambios → Observer.

Representar trabajo o estado

Petición como objeto → Command.
Instantánea para restaurar → Memento.
Recorrido independiente → Iterator.
Pequeño lenguaje de reglas → Interpreter.
Nueva operación sobre tipos estables → Visitor.

No existe una correspondencia automática. Pregunta por el orden, los errores, el ciclo de vida y las pruebas. Dos patrones pueden colaborar, pero cada uno debe justificar su coste.

Práctica y criterio / 66

Misma forma, motivos distintos

Piensa primero

A. Una capa comprueba permisos antes de leer un archivo.

B. Una capa comprime el contenido y otra lo cifra.

C. Un adaptador conecta una librería antigua a tu interfaz.

Respuesta razonada

A → Proxy: controla el acceso al objeto real.

B → Decorator: combina responsabilidades. El orden de comprimir y cifrar importa.

C → Adapter: traduce un contrato existente. No es Bridge: no estamos diseñando dos dimensiones independientes.

Pregunta extra: ¿poner logging en una capa la convierte siempre en Decorator? No: depende de su intención dentro del diseño, no solo de su estructura.

Práctica y criterio / 67

Lee el cambio de responsabilidad

Resuelve

  1. En State, pulsas tres veces el reproductor desde detenido. ¿Qué imprime?
  2. En Observer, eliminas unsubscribe. ¿Qué sucede con el segundo mensaje?
  3. En Memento, guardas la lista mutable sin copiarla. ¿Qué contiene el historial después de add?

Respuesta

  1. reproduce, detiene, reproduce. Cada pulsación cambia el modo que atiende la siguiente.
  2. También se entrega: la referencia sigue suscrita y puede quedar retenida en memoria.
  3. Comparte la lista editada y deja de ser una instantánea. Copia al guardar y al restaurar; evita elementos mutables compartidos.

Práctica y criterio / 68

Diseñar también es decir que no

Escenario

Una pequeña tienda tiene un único descuento fijo y solo acepta reservas locales. Se propone crear diez estrategias, un Singleton global y reintentar cada reserva cinco veces.

¿Qué mantendrías? ¿Qué riesgo concreto introduce cada propuesta?

Respuesta

Empezaría con una función para el descuento y un caso de uso claro. Introduciría Strategy al aparecer políticas realmente diferentes.

Inyectaría el almacenamiento en vez de hacerlo global. Reintentar una escritura puede duplicar reservas: primero hace falta una garantía de idempotencia, no más intentos.

Una prueba que verifica una sola reserva aporta más que varias capas sin un problema real.
